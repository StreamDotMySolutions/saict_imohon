Project Understanding & Architecture Reference

Malaysian government (RTM) equipment request & distribution system · Generated 12 Aug 2026

A Malaysian government equipment request and distribution management system for RTM (Radio Televisyen Malaysia), deployed to imohon.rtm.gov.my. Staff submit equipment requests (permohonan) that pass through a multi-tier approval chain, then get distributed (agihan) with full delivery and acceptance tracking. All user-facing text is in Bahasa Malaysia; code identifiers are in English.

Stack & Shape

  • backend/ — Laravel 10 REST API (PHP 8.1+, MySQL). Sanctum token auth, Spatie Permission (6 roles) + Activity Log, nested-set categories & departments.
  • frontend/ — React 18 SPA (Create React App). Zustand state, React-Bootstrap 5, Axios with token interceptors.
  • Deployment — scripts/deploy.sh (git pull → composer install → npm build) behind nginx + PHP 8.2-FPM.
  • Branches — default dev branch is dev; work here is on claude/project-understanding-sufy7s.

The Two Core Workflows

1 · Permohonan (Request)  MOHON-{year}-{NNNN}
User drafts a request → submits → Manager approves → Admin processes & finalizes. A 4-step state machine tracked on MohonApproval (step/status), mirrored onto MohonRequest.
2 · Agihan (Distribution)  AGIHAN-{year}-{NNNN}
Admin creates a distribution request for an approved permohonan and assigns inventory items → Boss approves → Admin sets delivery info → User accepts delivery. Reference numbers are auto-generated in a model booted() hook.

MohonApproval state machine

stepstatusMeaningActor
0pendingDraft (not yet submitted)User
1pendingSubmitted, awaiting ManagerManager
2approved / rejectedManager decisionManager
3pending / approvedAdmin processingAdmin
4approved / rejectedFinal decision, ready for distributionAdmin

Audit-trail design: approval records are inserted, never updated in place — each step is a new row. Backend logic lives in a public static service layer (MohonService, MohonApprovalService, distribution services); controllers are thin and role-grouped under /api/{role}/…, wired in RouteServiceProvider.php.

Practical Gotchas — Where Code Diverges from the Docs

These are the things worth knowing before touching the code — verified against the actual source, beyond what CLAUDE.md describes.

AreaReality on the ground
Route-level RBAC (frontend) There is none. ProtectedRoute only checks auth + email verification. Roles merely change which navbar links appear — any logged-in user can navigate directly to any admin/boss URL. Access control is enforced server-side per role prefix, not in the SPA.
DB foreign keys Migrations have a pervasive typo — ->costrained() instead of ->constrained(). It is a silent no-op, so no FK constraints exist at the DB level; relationships are enforced only in Eloquent.
Dead "Application" subsystem ApplicationService, DistributionService, DistributionApprovalService, DistributionAcceptanceService, User::applications(), and LoginTest's /api/applications all reference Application/Distribution models that don't exist. Leftovers from a prior design renamed to "Mohon" — treat as dead code.
Mass assignment Domain models use $guarded, not $fillable (docs say fillable). Only UserDepartment declares an explicit $fillable.
Tests Pest 2, but domain coverage is essentially zero — only trivial example tests plus a broken LoginTest hitting a non-existent route. RefreshDatabase is commented out.
Frontend cruft The createResourceStore factory is imported nowhere (dead) — every page hand-rolls the same store ~20×. Versioned duplicates remain (Agihan vs Agihan-v2, MohonDistributionItem vs -v2). App is hard-gated behind REACT_APP_MODE==='production' and a 768px desktop-only block. Router lives entirely in index.js (no App.js).
Minor Duplicate admin distribution routes; two migrations share timestamp 2026_03_04_042748; the global.php route group lacks auth:sanctum at the group level.

Key Models & Relationships

  • User → UserProfile → UserDepartment (nested set). Roles via Spatie: user manager admin boss system guest
  • MohonRequest → many MohonItem (→ Category), many MohonApproval (ASC), many MohonDistributionRequest (DESC).
  • MohonDistributionRequest → many MohonDistributionApproval (→ boss), many MohonDistributionItem.
  • MohonDistributionItem → Inventory, Category, MohonItem; hasOne Delivery + hasOne Acceptance.
